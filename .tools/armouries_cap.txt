1. THE PROBLEM THE USER IS ACTUALLY SOLVING
--------------------------------------------------------------------------------
Large nations are too strong in this mod: too stable, too rich, infrastructure costs
the same regardless of size, they can stay rural and collect more pop growth, and
they own more towns and therefore more armouries. The armory cap is one symptom.

The user's stated target behaviour:
  * if you are SMALL you should urbanize, and urbanization should give you better pop
    growth, development, manpower and wealth than a wide nation gets from it;
  * if you are WIDE you should lean rural, and rural should give you more income and
    better pop growth than hyperurbanizing would;
  * a WIDE nation must not be able to abuse the tall mechanics by hyperurbanizing.

--------------------------------------------------------------------------------
2. DESIGN DECISIONS (settled - do not re-litigate)
--------------------------------------------------------------------------------
2.1 The armory cap is not hardcoded. It is a `max_levels` script value evaluated in
    the location scope, so it can read the owner's size. Vanilla chain:
      in_game/common/building_types/manpower_buildings.txt:82   armory = { ... }
      same file :86                                            max_levels = manpower_max_level
      in_game/common/script_values/building_caps.txt:461       manpower_max_level = 1 + 0.025 x population
    (line numbers unverified here - see section 5).

2.2 Every scalar "size of nation" metric was examined and REJECTED as a gate. Record
    the reasons so they are not retried:
      * num_locations          - moves on every conquest; "small" in 1337 is not "small"
                                 in 1700; a rural sprawler looks small until it is not.
      * total_population /     - these measure the LAND, not the player's choice: a
        total_development /      25-dev Florence is 30% of Tuscany, a 25-dev Isfahan is
        wealth                   5% of Persia. Same number, opposite meaning. Italy vs
                                 Persian mountains is the user's own test case.
      * avg control /          - volatile AND backwards: sprawlers have LOW control, so
        total_control_scaled_     a control-based test hands the bonus to the exact
        population               nation it is meant to starve.
      * country_rank_level     - upgrading rank is a CHOICE, so a 60-location realm can
                                 sit on "Duchy" forever and opt into the buff.
      * country_power_score    - a genuinely tall minor scores as a Major, so it loses
        (mp_limits_values.txt)   the bonus exactly when it should apply.
      * percentile / rank      - era-proof by construction, but it moves because of
        among contemporaries    OTHER people's conquests, and the mod's machinery is
                                 gated behind `mp_mechanics_enabled` and can exclude
                                 AI from the tier lists. Also not sim-modellable.
    Absolute thresholds of any kind are wrong twice: in 1337 everyone qualifies (feature
    inert), in 1700 nobody does (feature dead), and they need re-tuning per age, per
    DLC and per map change.

2.3 CHOSEN SHAPE: price urbanization, never gate it. A gate has a cliff to sit under,
    is illegible in MP and is unteachable to the AI. A price curve means the abuse IS
    the cost: a wide nation may hyperurbanize, but it pays inflated urban cost,
    throttled migration, starved provinces and idle staffing while forgoing the rural
    curve it would otherwise be riding. There is no arbitrage window because the two
    curves are complements.

2.4 The curves ride on throttles the engine already has (do not invent new ones):
      * FOOD      - urban pops eat ~4x what peasants eat (memory.md:1286); starving
                    provinces take province_starving at -5%/yr growth. Rural-heavy
                    realms already have the surplus.
      * MIGRATION - towns grow by pulling pops in (non_rural_migration_attraction vs
                    rural_migration_attraction). Slow the urban pull and each new town
                    fills over decades.
      * STAFFING  - building output = modifier x level x goods access x staffing. An
                    unfilled town produces nothing but still costs upkeep.

2.5 The armory cap becomes a RIDER on the urban curve, not a special rule. Manpower is
    split along the same axis: WIDE -> levies (global_levy_size_modifier; vanilla's
    quality_vs_quantity right side already does this), TALL -> standing pool (armory /
    barracks cap). That is the whole answer to "should small nations have more
    armouries": yes, as the manpower expression of the urban curve.

2.6 A hard "stance" gate exists if a binary is ever wanted (societal values, section
    4), but it is NOT needed for the agreed design. Do not add it unasked.

3. IMPLEMENTATION PLAN (ordered)
--------------------------------------------------------------------------------
Step 0 - resolve the unverified primitives first (section 6). If any fails, stop and
         report rather than inventing a workaround.

Step 1 - the single dimensionless knob, in in_game/common/script_values/
         abm_building_caps.txt (append after abm_starting_manpower_max_level, :52):

  # 1.0 at no land, 0.0 at this age's "wide" mark, smooth in between.
  # TWO definitions are needed, because the value is read from two scopes:
  #   abm_smallness        - country scope, for the country auto-modifiers (Step 2/3)
  #   abm_smallness_in_loc - location scope, for max_levels and location auto-modifiers
  # The location one must read the owner's land: `owner.num_locations` (dotted country
  # value from location scope - vanilla precedent building_caps.txt:99/:134/:273 use
  # owner.modifier:..., so the shape is proven, the exact key is not - see 6.2).
  abm_smallness = {
      value = 1
      subtract = { value = num_locations divide = abm_width_mark min = 1 }
      max = 0
  }
  abm_smallness_in_loc = {
      value = 1
      subtract = { value = owner.num_locations divide = abm_width_mark min = 1 }
      max = 0
  }

  # ONE number to tune for the whole feature. Grows with the era so the definition of
  # "wide" grows with it (the mod's own precedent: mp_limits_assign_category_markers
  # uses per-age population thresholds 350/350/500/700/1000/1000,
  # scripted_effects/abm_scripted_effects.txt:322).
  abm_width_mark = {
      value = @abm_width_base
      if = { limit = { current_age_or_later = { age = age_2_renaissance } } multiply = 1.5 }
      if = { limit = { current_age_or_later = { age = age_3_discovery } }   multiply = 1.5 }
      if = { limit = { current_age_or_later = { age = age_4_reformation } } multiply = 1.5 }
      if = { limit = { current_age_or_later = { age = age_5_absolutism } }  multiply = 1.5 }
      if = { limit = { current_age_or_later = { age = age_6_revolutions } } multiply = 1.5 }
  }

  @abm_width_base is the only balance number in the design. Pick it from real saves
  (the location simulator / from_save.js can dump location counts per date).

  `abm_wideness` (the complement) must be derived the same way, as a second named value
  (1 - abm_smallness), because `scales_with` takes a value name, not an expression.

Step 2 - URBAN curve: a country auto-modifier scaled by abm_smallness, in
         in_game/common/auto_modifiers/ (same file or a new abm_tall_wide.txt).
         Precedent for scales_with: in_game/common/auto_modifiers/abm_country.txt:26
         (REPLACE:num_locations_impact, scales_with = { value = num_locations divide = 20 }).

  scales_with = { value = abm_smallness }   # 1.0 small .. 0.0 wide
    global_non_rural_monthly_development   # urban development (compounds: dev -> capacity)
    global_non_rural_monthly_prosperity
    non_rural_migration_attraction
    global_burghers_desired_pop_scaled     # keep the urban share high
    (optional) global_production_efficiency, global_building_establishment_speed

  URBAN POP GROWTH: there is NO urban-only population-growth country modifier.
  It must be a LOCATION auto-modifier with potential_trigger = { is_city = yes }
  carrying local_population_growth, scaled by abm_smallness_in_loc. `is_city` is vanilla's
  urban test and INCLUDES towns (memory.md:1286); the mod already uses is_city
  filters in a location_modifier (government_reforms/abm_gov_reforms_general.txt:108).

Step 3 - RURAL curve: a second auto-modifier scaled by abm_wideness.
  scales_with = { value = abm_wideness }
    global_raw_material_output
    global_max_rgo_size_modifier_in_rural
    global_rural_build_buildings_cost      # NEGATIVE: rural construction gets cheaper
    rural_migration_attraction
    global_levy_size_modifier              # wide = levies (see 2.5)
    (optional) global_peasants_rural_desired_pop, global_monthly_development

  URBAN BUILD COST: there is no non-rural country build-cost modifier (only
  global_rural_build_buildings_cost exists), so "urban construction gets dearer as you
  grow" needs a LOCATION auto-modifier with potential_trigger = { is_city = yes }
  carrying local_build_new_buildings_cost, scaled by abm_wideness_in_loc
  (the location-scope complement, defined the same way as abm_smallness_in_loc).

Step 4 - the armory itself, as a rider on the urban curve.
  Add to step 2's urban block (or read directly in the cap value):

  abm_armory_max_level = {
      value = manpower_max_level              # vanilla base, untouched
      add = {
          desc = "abm_building_level_armory_tall"
          value = abm_armory_extra          # e.g. 2, scaled by smallness
          multiply = abm_smallness_in_loc   # location scope: reads owner.num_locations

  OPTIONAL BOUND on the realm total (prevents an 8-town realm from getting 8x the
  gains; also makes the rule shrink-proof, since releasing towns re-divides a constant

      abm_armory_extra = { value = 6 divide = { value = abm_urban_location_count min = 1 } min = 2 }
      abm_urban_location_count = { value = 0 every_owned_location = { limit = { is_city = yes } add = 1 } }

  Pointing the building at the value: use a FULL `REPLACE:armory`, not `INJECT:`.
    - INJECT in building_types has NO vanilla precedent and the mod's only
      building_types INJECT (stud farm) is itself still unverified in game

  Scope note: the armory is obsoleted by barracks in Age IV and barracks uses the SAME

  (.tools/eu5/advances/1_building_unlocks.txt:718-762). armory_advance carries
  ai_weight = 2000, so the AI leans into armories hard.
- Over-cap levels are never demolished ("EU5 Location Mechanics (1.4.4).md":54,
  Sevilla has 7 armories over a cap of 4). Any cap change only gates NEW levels, and
  that is what makes a shrinking metric harmless and a growing metric painless.

5. FROM THE EARLIER AUDIT - UNVERIFIED HERE, RE-CHECK BEFORE QUOTING
--------------------------------------------------------------------------------
- manpower_max_level is shared by FIVE buildings: armory (:86), training_fields (:141),
  barracks (:188), regimental_camp (:239), conscription_center (:288); D009 adds
  saqaliba_barracks on the same value. Do NOT retune the shared value - give the armory
  its own cap and leave the other four vanilla.
- Armory is town/city/megalopolis only; rural locations cannot build it.
- local_manpower per armory level = 0.01. Pool = monthly income x 60
  (MAX_MANPOWER_YEARS 5), so +6 levels realm-wide (~+60 men/month) is about +3.6k max
  manpower. Quote the pool effect, not the monthly trickle, when discussing balance.
- One armory level costs firearms 0.5, leather 0.5, cloth 0.10, paper 0.20,
  weaponry 0.5 and consumes part of the location's total building-level budget
  (town 25 / city 100 / megalopolis 200 from location_ranks/00_default.txt).
  In towns that budget is generous, so "the levels compete for the slot budget" is a
  WEAK self-limiting argument - do not lean on it.
- The audit's own claims that `owner ?= { ... }` and `owner.<value>` work inside a
  script value rest on vanilla building_caps.txt uses (:99/:134/:273 owner.modifier:
  market_building_levels, :404 owner = { has_variable = ... }) and on the mod's
  remove_if idiom. Verify with the first in-game test.
- Biggest MISS of the earlier audit: staffing. Armory output is scaled by staffing and
  needs soldier pops; memory.md:472 records that a 3-level capital building
  under-staffs in a small capital. A 20-25k town in a small nation may not have the
  soldiers for level 2-3 at all, which would make the whole feature inert. Test this
  before tuning numbers.

6. KNOWN-UNKNOWNS - RESOLVE BY PLAYING, IN THIS ORDER
--------------------------------------------------------------------------------
1. Does `scales_with` accept a named mod script value (abm_smallness) and apply it to a
   normal (non-impact) auto-modifier? Closest precedent: scales_with = { value =
   stability } in vanilla auto_modifiers.
2. Does a dotted country value resolve from location scope in a script value
   (`owner.num_locations`, `owner.total_development`)? Vanilla precedent exists for
   `owner.modifier:...` and for `owner = { ... }` as a limit, but not for a plain
   dotted country value inside a location-scope value. This is what `abm_smallness_in_loc`
   depends on (see Step 1); `owner ?= { num_locations <= N }` in a `limit` is the
   fallback shape if the dotted form fails.
3. Does a LOCATION auto-modifier with potential_trigger = { is_city = yes } exist and
   fire? This is load-bearing for urban growth and urban build cost.
4. Do `min =` and `max =` work as operators inside a script value block (outside
   max_levels)? The stud-farm cap uses max = 1 inside max_levels only.
5. Does `every_owned_location = { limit = { is_city = yes } add = 1 }` work inside a
   script value, and is it cheap enough to evaluate per tooltip?
6. Does an owner-based max_levels evaluate correctly, and is there no error-log spam
   (logs/error.log rotates; the fresh chunk takes the lowest free number)?
7. Does REPLACE:armory with an external abm_armory_maintenance produce no duplicate-id
   or duplicate-PM error?
8. Staffing: can a 20-25k town actually fill armory levels 2-3 with soldier pops?

8. DON'TS
--------------------------------------------------------------------------------
- Do not retune manpower_max_level (five buildings share it).
- Do not use INJECT: in building_types as the first attempt.
- Do not define the same building or PM id twice.
- Do not edit the replaced copy production_methods/unsorted_building_inputs.txt.
- Do not reuse mp_is_minor / mp_is_small for a universal rule.
- Do not gate on country rank (it is opt-out) or on average control (it is backwards).
- Do not hardcode an absolute size threshold without the age-stepped multiplier.
- Do not edit p_building_age_* prices - they reprice every building in the game.
- Do not ship the armory rule without resolving unknown 8 (staffing) first; it decides
  whether the feature does anything at all.
